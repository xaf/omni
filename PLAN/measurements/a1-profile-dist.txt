CAVEAT: this is a glibc host build, not a shipped target
--------------------------------------------------------
Absolute sizes here are NOT comparable to the shipped musl binary
(/usr/local/bin/omni, 28,912,144 bytes). Different target, different libc,
and different openssl handling. The 36.3% delta should be representative of
what lto+cgu1+strip achieves, but re-measure on musl in CI to confirm.

Incidental finding, relevant to the openssl experiment
------------------------------------------------------
On this gnu target:

  - `openssl-sys` and `openssl` ARE compiled
      grep "Compiling openssl" -> openssl-sys v0.9.117, openssl v0.10.81
  - there is NO openssl-src build directory
      -> the `vendored` feature did not engage; openssl-sys found the
         system library via pkg-config instead
  - the final binary contains ZERO openssl symbols and NO version banner
      nm  | grep -c "OPENSSL_init\|SSL_CTX_new"  -> 0
      strings | grep -cE "OpenSSL [0-9]+\."      -> 0
  - ldd shows only libc, libgcc_s, libm -- no libssl, no libcrypto

So on gnu the linker discards openssl entirely as dead code, and the binary
works. That is supporting evidence for the "openssl is orphaned" hypothesis,
but it is NOT conclusive for the shipped targets:

  the shipped musl binary DOES contain "OpenSSL 3.5.4 30 Sep 2025"

because on musl there is no system openssl, so `vendored` engages,
openssl-src builds the full library, and static archive linkage pulls at
least the object carrying the version banner into the binary.

=> The openssl experiment (PLAN/01-binary-size.md item 2) MUST be run on a
   musl target. A local gnu build cannot settle it.
