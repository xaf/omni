# Phase A: CI - profile split and regression gates

**Goal:** PR CI and local dev stay fast; only the release build pays for maximum optimisation. Add gates so size, linking, and prompt latency cannot silently regress.

**Status:** not started

## Current state

Chain: `release.yaml:56` → `build.yaml` (matrix) → `build-and-test-target.yaml` (actual build).

Targets (`build.yaml:50-65`): `{aarch64,x86_64}-unknown-linux-musl`, `{aarch64,x86_64}-apple-darwin`, built via `houseabsolute/actions-rust-cross@v1` (`build-and-test-target.yaml:99-101`).

Build step (`:137-150`):

```yaml
env:
  OMNI_RELEASE_VERSION: ${{ inputs.release_version }}
  RUSTFLAGS: "-C prefer-dynamic=no"
with:
  command: build
  args: "--locked --release"
  strip: true
```

So: plain `--release` with Cargo defaults ([`00-findings.md`](00-findings.md#build-configuration)), and `strip: true` is the **only** size optimisation. No `lto`, no `codegen-units`, no section GC.

Existing gates: `cargo machete` (`tests.yaml:185-209`, required via `:279,291`), clippy, `cargo test`, and a bats suite (`:243-286`, `--jobs 8`). **No size gate, no linking gate, no performance gate.**

## 1. Profile split

Per decision **D7**, add `[profile.dist]` (defined in [`01-binary-size.md`](01-binary-size.md#1-add-profiledist)) and use it **only** for releases:

| Path | Profile | Rationale |
|---|---|---|
| PR CI, `cargo test`, local dev | `release` (cheap) | fast iteration; `lto = "fat"` + `codegen-units = 1` are slow to compile |
| Release build | `dist` | maximum optimisation, shipped once per release |

Change the release build step to `args: "--locked --profile dist"`.

**Gotcha:** `--profile dist` outputs to `target/dist/`, not `target/release/`. Every downstream step needs its path updated:

- `tar czvf` packaging (`:154`)
- `sha256sum` (`:158-161`)
- cosign keyless signing (`:164-172`)
- the binary smoke tests (`omni help`, `omni status`, `:243-286`)

Grep the workflow for `target/release` before and after; a missed path fails confusingly (packaging a stale or absent binary).

## 2. Fix the double compile

`build-and-test-target.yaml:123-135` runs `command: test` with `args: "--locked --release"`, then `:137-150` runs `command: build` with the same profile. That compiles the graph twice, and the test pass additionally builds dev-dependencies - `mockito` (`Cargo.toml:30`) pulls its own tokio and an HTTP server, so `cargo test --release` compiles a materially larger graph than `cargo build --release`.

With the profile split this gets worse, not better: tests on `release`, build on `dist` means **two full compiles with different codegen settings** and no shared artifacts.

Options:

- **(a)** Split into separate jobs: a `test` job on the cheap profile, a `dist` build job. Parallel, clear, but the `dist` compile is not cached from the test compile (it cannot be - different profile).
- **(b)** Run tests once on a single cheap target (they are platform-independent for the most part) and only cross-build `dist` per target. Requires confidence that per-target test runs are not catching target-specific bugs - **check git history for target-specific test failures before assuming this.**

Prefer (a) unless CI wall-clock is a pressing problem. Do not silently drop per-target testing.

## 3. Fix cache invalidation

`Swatinem/rust-cache@v2` is configured with `shared-key: omni-build` (`:89-92`), and both action steps set `use-rust-cache: false` to avoid double-caching.

But `:118-121` rewrites the version into `Cargo.toml` **and** `Cargo.lock` with `perl -i -pe`, **after** cache restore. That changes the manifest hash, which is part of the cache key - undermining cache hits on every release build.

The version is *also* injected via `OMNI_RELEASE_VERSION` (`:140`), which `build.rs:7` already honours (`cargo:rerun-if-env-changed=OMNI_RELEASE_VERSION`, consumed at `build.rs:9-22`).

So either:

- move the `perl` rewrite **before** cache restore, or
- **drop the rewrite entirely** and rely on `OMNI_RELEASE_VERSION` alone

The second is cleaner. Verify what actually needs the rewritten `Cargo.toml` - most likely only `cargo package` / crates.io publishing, which is a separate workflow (`.omni.yaml:105` has a `cargo-package` command). If so, scope the rewrite to that path only.

## 4. `build.rs` invalidation

`build.rs:7` emits `cargo:rerun-if-env-changed=OMNI_RELEASE_VERSION` as its **only** rerun directive. Because *any* `rerun-if-*` directive is present, Cargo's default "rerun on any change in the package directory" heuristic is **disabled**. There is no `rerun-if-changed` for git state, so the embedded version can go stale unpredictably.

Add `cargo:rerun-if-changed=.git/HEAD` and the relevant refs path. Note the script emits `cargo:rustc-env=CARGO_PKG_VERSION` (`:24`), so whenever it *does* rerun with a changed value, **the entire crate recompiles** - which is correct, but means invalidation should be precise rather than accidental.

Also drop the `[build-dependencies] time` with `serde-well-known` (`Cargo.toml:27`), used only for a fallback timestamp at `build.rs:9-22`. `std::time` removes a host-side compile of `time` + `serde` + `time-macros` before the crate can build.

## 5. New gate: static linking

Full design in [`02-static-linking.md`](02-static-linking.md). Runs immediately after the build and **before** packaging/signing, on all four targets, on both the PR and release paths.

## 6. New gate: binary size

Record the size per target and fail if it grows beyond a threshold versus a stored baseline.

- Store the baseline in-repo (a small JSON/TOML per target) so the gate is reviewable and updated deliberately in a PR.
- Allow a tolerance band (a few percent) so noise does not block.
- Print the delta in the job summary either way, so size becomes visible on every PR.
- Keep `cargo bloat --release --crates` output as a CI artifact for attribution when it does grow.

This is what makes the [`01-binary-size.md`](01-binary-size.md) measurement table trustworthy over time rather than a one-off.

## 7. New gate: prompt latency

The most user-visible performance property ([`06-runtime-speed.md`](06-runtime-speed.md)), currently unmeasured.

Benchmark `omni hook env bash` in a fixture repo containing an `.omni.yaml` with an `up:` block (mirroring `/app`, which measures 13.6 ms today) with `OMNI_SHELL_PPID` set - that is what the real shell hook does, and it is the difference between 5.8 ms and 7.2 ms.

Caveats to design around:

- **CI runners are noisy.** Use a generous threshold and many iterations; treat it as a *regression* gate (catching a 2x blowup), not a precision benchmark.
- Report the number in the job summary regardless of pass/fail, so trends are visible.
- Warm the page cache first - the first invocation is not representative.
